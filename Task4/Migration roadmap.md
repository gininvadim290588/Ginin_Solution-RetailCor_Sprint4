# План миграции (Migration Roadmap)

## Цель

Выполнить поэтапную трансформацию платформы RetailCore без остановки критичных бизнес-процессов, минимизируя риски и сохраняя обратную совместимость.

---

# Принципы миграции

- отсутствие Big Bang миграции;
- непрерывная работа платформы;
- обратная совместимость API;
- постепенная декомпозиция монолита;
- минимизация изменений в критичных бизнес-процессах;
- использование Strangler Fig Pattern;
- наблюдаемость каждого этапа;
- возможность отката после каждого этапа.

---

# Roadmap

| Этап | Изменения | Зависимости | Основные риски | Критерии завершения |
|------|-----------|-------------|----------------|---------------------|
| 1 | Архитектурное обследование платформы, восстановление документации, описание доменных границ | Нет | Неполная информация о системе | Подготовлена актуальная архитектурная документация, описаны доменные области и зависимости |
| 2 | Развертывание API Gateway (Integration Layer) перед монолитом | Этап 1 | Нарушение существующих интеграций | Все внешние запросы проходят через API Gateway, функциональность сохранена |
| 3 | Внедрение централизованной наблюдаемости (логирование, мониторинг, трассировка) | Этап 2 | Недостаточная полнота мониторинга | Доступны метрики, централизованные логи и распределенная трассировка для основных сценариев |
| 4 | Внедрение Event Bus и публикация доменных событий монолитом | Этапы 2–3 | Неконсистентность событий | Монолит публикует события без изменения существующей бизнес-логики |
| 5 | Выделение Notification Service | Этап 4 | Потеря уведомлений | Уведомления формируются новым сервисом, основной процесс не изменился |
| 6 | Выделение Analytics Service и отказ аналитики от прямого доступа к Oracle | Этап 4 | Неполнота данных в аналитике | Аналитика получает данные через события, нагрузка на Oracle снижена |
| 7 | Выделение Order Status Service | Этапы 4–6 | Несогласованность статусов между новым сервисом и монолитом | Новый сервис является владельцем жизненного цикла заказа, данные синхронизированы |
| 8 | Постепенная замена интеграций через Shared Database на API и события | Этап 7 | Ошибки взаимодействия сервисов | Основные интеграции переведены на API и событийную модель |
| 9 | Подготовка к декомпозиции бизнес-модулей (Pricing, Promo, Delivery) | Этап 8 | Высокая связанность модулей | Подготовлены планы выделения следующих сервисов |
| 10 | Подготовка миграции с Oracle на целевую платформу хранения данных | Этап 9 | Потеря данных, длительный простой | Подготовлена стратегия миграции, Oracle остается резервным источником данных до завершения перехода |

# Промежуточные состояния

## После этапа 2

- монолит остается основным компонентом;
- внешние системы взаимодействуют только через API Gateway.

---

## После этапа 4

- появляется событийная архитектура;
- монолит начинает публиковать доменные события.

---

## После этапа 7

- управление статусами заказа вынесено в отдельный сервис;
- Notification Service и Analytics Service работают независимо;
- Oracle остается основной транзакционной БД.

---

## После этапа 10

- подготовлена платформа для дальнейшей декомпозиции;
- критичные процессы продолжают работать в монолите;
- дальнейшая миграция выполняется по доменным областям.

---

# Архитектурные пробелы

Во входных данных отсутствуют:

- допустимое окно миграции;
- требования к времени переключения;
- допустимое время деградации;
- требования к двойной записи;
- требования к синхронизации данных;
- требования к RTO/RPO;
- требования к SLA новой архитектуры.

Эти параметры необходимо уточнить у инфраструктурной команды, команды эксплуатации и бизнес-спонсора до начала реализации.
