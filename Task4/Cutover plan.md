# Cutover Plan

## Переход

Выделение Order Status Service и переключение управления статусами заказа на новый сервис.

---

# Цель переключения

Передать ответственность за жизненный цикл заказа новому сервису без остановки обработки заказов и без нарушения существующих интеграций.

---

# Причина выбора

Управление статусами имеет четкие предметные границы и является одной из наиболее проблемных областей текущей системы:

- расхождение документации с фактическим поведением;
- большое количество ручных операций;
- дублирование логики;
- сложность сопровождения.

---

# Условия начала переключения

До начала переключения должны быть выполнены следующие условия:

- успешно завершено интеграционное тестирование;
- проведено нагрузочное тестирование нового сервиса;
- настроены мониторинг, логирование и трассировка;
- подготовлены резервные копии данных;
- выполнена синхронизация данных между Oracle и Status DB;
- подтверждена готовность всех участников переключения.

---

# Роли и ответственность

| Роль | Ответственность |
|------|-----------------|
| Руководитель проекта | Принятие решения о начале переключения |
| Архитектор решения | Координация процесса, контроль соответствия архитектуре |
| Team Lead команды заказов | Переключение бизнес-логики |
| DevOps-инженер | Развертывание новой версии, изменение конфигурации |
| DBA | Контроль состояния Oracle и Status DB |
| QA | Проверка бизнес-сценариев |
| Команда эксплуатации | Мониторинг платформы |
| Служба поддержки | Контроль обращений пользователей |

---

# Пошаговый сценарий

## Шаг 1

Подтвердить готовность участников.

---

## Шаг 2

Убедиться, что синхронизация данных между Oracle и Status DB завершена без ошибок.

---

## Шаг 3

Включить публикацию событий изменения статусов из монолита.

---

## Шаг 4

Перевести Order Status Service в режим активной обработки запросов.

---

## Шаг 5

Изменить маршрутизацию API Gateway таким образом, чтобы запросы управления статусами направлялись в новый сервис.

---

## Шаг 6

Включить запись статусов в новую базу данных.

---

## Шаг 7

Оставить чтение статусов из Oracle в режиме резервной проверки (Dual Read) до подтверждения корректности работы нового сервиса.

---

## Шаг 8

После успешной проверки отключить использование Oracle для чтения статусов.

---

# Проверки после переключения

Необходимо убедиться, что:

- новые заказы получают корректные статусы;
- переходы между статусами выполняются согласно бизнес-правилам;
- количество ошибок не увеличилось;
- отсутствуют расхождения между Oracle и Status DB;
- уведомления продолжают отправляться корректно;
- интеграции с ERP, платежными системами и службами доставки работают без изменений;
- отсутствует деградация производительности.

---

# Наблюдаемость

Во время переключения контролируются:

- ошибки приложения;
- время ответа API;
- успешность обработки событий;
- очередь сообщений;
- количество необработанных сообщений;
- состояние Oracle;
- состояние Status DB;
- журналы приложения;
- распределенная трассировка.

---

# Rollback-сценарий

Переключение отменяется при возникновении одного или нескольких условий:

- критические ошибки обработки статусов;
- потеря данных;
- нарушение бизнес-процессов;
- отказ интеграций;
- значительное увеличение количества ошибок.

---

## Порядок отката

1. Переключить API Gateway обратно на монолит.
2. Остановить запись в Status DB.
3. Продолжить обработку статусов средствами монолита.
4. Проверить целостность данных Oracle.
5. Проанализировать причины отказа.
6. Подготовить план повторного переключения.

---

# Архитектурные пробелы

Во входных материалах отсутствуют следующие параметры:

- допустимое окно переключения;
- максимальная длительность переключения;
- допустимое время деградации;
- критерии успешности по SLA/SLO;
- требования к RTO и RPO;
- допустимое количество ошибок во время переключения.

Эти требования необходимо согласовать с бизнес-спонсором, командой эксплуатации и владельцем процесса обработки заказов до проведения cutover.
