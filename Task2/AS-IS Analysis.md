# RetailCore — Анализ текущего состояния (AS-IS)

## 1.Основание для реконструкции текущего состояния

Анализ собран по следующим источникам:

- описание кейса RetailCore и приложенная AS-IS диаграмма;
- стенограмма интервью с бизнес-спонсором проекта, где зафиксированы цели трансформации, ограничения и критерии ценности;
- стенограмма интервью с руководителем клиентской поддержки, где описаны проблемы прозрачности, ручные операции и ошибки в статусах;
- три стенограммы разработчиков из `interview.zip`:
  - технический лидер монолита;
  - разработчик логистических и партнёрских интеграций;
  - разработчик аналитики и отчётности;
- фрагмент `OrderProcessingService.java`, который показывает фактический стиль реализации и зависимости в коде.

## 2.Основные потоки данных

| Поток | Смысл |
|---|---|
| Клиент → каналы → монолит | Оформление заказа и просмотр статуса |
| Монолит → Oracle | Сохранение заказа, статусов, служебных атрибутов, правил и legacy-данных |
| Монолит → платёжные провайдеры | Создание платёжной сессии |
| Монолит → службы доставки | Резервирование/подтверждение слота доставки |
| Монолит → маркетплейсы | Партнёрские сценарии и вариации заказа |
| Монолит → .NET integration service | Обмен через staging/shared tables |
| Монолит / Oracle → аналитика | Выгрузки, отчёты, исторические данные |
| Поддержка → монолит / админка | Ручные исправления, технические статусы, разбор исключений |

### Проблемные зоны и зависимости

| Зона | Суть проблемы |
|---|---|
| Oracle | Shared DB, многоролевое использование, узкое место, интеграционный и аналитический хаб |
| Монолит | Накопленная оркестрация и смешение ответственности |
| Статусы заказа | Нет единого централизованного жизненного цикла |
| Support / Admin tools | Ручные вмешательства, компенсация архитектурных пробелов |
| Аналитика | Нет единой канонической модели, данные читаются из неоднородных источников |
| Логистика | Правила распределены по коду, Oracle, конфигу и batch-скриптам |
| Интеграции | Смесь REST, очередей, batch и таблиц, отсутствие унификации |

###  Что особенно важно зафиксировать по текущему состоянию

1. Платформа уже стала центром почти всех операций.
2. Ядро не просто исполняет заказ, а оркестрирует связанные сценарии.
3. Oracle — не только БД, а фактически часть архитектуры интеграций.
4. У платформы нет одного достоверного представления заказа и его статусов.
5. Поддержка и смежные команды вынуждены восполнять архитектурные пробелы процессом и ручными действиями.
6. Аналитика и операционный контур мешают друг другу через общую БД.
7. Любая трансформация должна сохранять работоспособность критических сценариев.

## 3. Итоговый вывод по текущему состоянию

RetailCore сейчас — это не набор независимых сервисов, а платформа, в которой Java-монолит и Oracle формируют центральный узел почти всех критичных потоков. Внутри этой связки находятся оформление заказа, промо, доставка, оплаты, статусы, ручные коррекции, отчётность и часть аналитики.

Главные ограничения для изменений:

1. высокая связность;
2. shared database pattern;
3. отсутствие единой модели заказа и статусов;
4. смешение операционных, интеграционных и аналитических обязанностей;
5. dependence on manual and semi-manual recovery paths;
6. отсутствие количественно зафиксированных SLO/RTO/RPO и требований к производительности.

Именно поэтому текущий этап должен не “проектировать идеальное будущее”, а точно зафиксировать, как система реально устроена сейчас, где у неё границы, и какие участки нельзя трогать без подготовки поэтапной миграции.
