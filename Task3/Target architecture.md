# Проработка целевой архитектуры RetailCore

## 1. Подход к трансформации

На основании анализа текущего состояния принято решение отказаться от стратегии полной переписи (Big Bang Rewrite).

Причины:

- система является критически важной для бизнеса;
- отсутствует полная документация;
- имеются скрытые зависимости;
- значительная часть знаний находится у отдельных сотрудников;
- Oracle используется одновременно как операционная база данных и интеграционный механизм;
- изменение ядра обработки заказов связано с высоким риском остановки бизнеса.

Поэтому целевая архитектура представляет собой промежуточное состояние, в котором новые компоненты постепенно выделяются вокруг существующего монолита по паттерну **Strangler Fig**.

---

# 2. Точки трансформации

## Точка 1. Выделение интеграционного слоя

### Проблема

В настоящее время большинство внешних систем интегрируются непосредственно с монолитом.

Это приводит к:

- высокой связанности;
- сложному сопровождению;
- невозможности независимого изменения интеграций.

### Решение

Создать Integration Layer (Integration Service/API Gateway).

Он станет единой точкой взаимодействия:

- интернет-магазина;
- маркетплейсов;
- платежных систем;
- служб доставки.

### Почему подходит

Интеграции имеют относительно небольшое количество зависимостей от внутренней бизнес-логики.

### Риски

- изменение контрактов API;
- необходимость обеспечить обратную совместимость.

---

## Точка 2. Выделение сервиса управления статусами заказа

### Проблема

Управление статусами распределено между несколькими компонентами.

Документация не соответствует фактическому поведению.

Большое количество ручных операций связано именно со статусами.

### Решение

Создать отдельный Order Status Service.

Он станет единым владельцем жизненного цикла заказа.

### Почему подходит

Статусы являются самостоятельной предметной областью.

Имеют понятные границы.

### Риски

- скрытые переходы статусов;
- большое количество исторических сценариев.

Перед миграцией необходимо полностью восстановить State Machine.

---

## Точка 3. Выделение сервиса уведомлений

### Проблема

Уведомления встроены в бизнес-процесс.

Это увеличивает время обработки заказа.

### Решение

Создать Notification Service.

Использовать асинхронную обработку событий.

### Почему подходит

Сервис практически не влияет на бизнес-транзакции.

### Риски

Минимальные.

---

## Точка 4. Выделение аналитики

### Проблема

Python Analytics обращается напрямую к Oracle.

Это увеличивает нагрузку на транзакционную базу данных.

### Решение

Создать отдельный контур аналитики.

Передача данных осуществляется через события.

### Почему подходит

Аналитика не участвует в критическом бизнес-процессе оформления заказа.

### Риски

Низкие.

---

## Точка 5. Отказ от интеграции через общую базу данных

### Проблема

Большинство компонентов используют Shared Database.

### Решение

Постепенно заменить обмен через Oracle на API и события.

### Почему подходит

Позволяет уменьшить связанность системы.

### Риски

Высокие.

Переход должен выполняться постепенно.

# Матрица зависимостей (Problem → Impact → Transformation → Metric)

| № | Проблема (AS-IS) | Влияние на бизнес и архитектуру | Точка трансформации | Метрика успеха |
|---|------------------|---------------------------------|---------------------|----------------|
| 1 | Внешние системы интегрируются напрямую с монолитом | Высокая связанность, сложность изменения интеграций, длительное подключение новых партнеров | **Выделение Integration Layer (API Gateway)** | Сокращение времени подключения новой интеграции; уменьшение количества прямых интеграций с монолитом |
| 2 | Отсутствуют четкие границы жизненного цикла заказа, статусы реализованы в разных компонентах | Несогласованность статусов, большое количество ошибок и ручных операций, сложность сопровождения | **Выделение Order Status Service** | Уменьшение количества ручных корректировок статусов; наличие единого источника состояния заказа |
| 3 | Уведомления встроены в основной процесс обработки заказа | Увеличение времени обработки заказа, сильная связанность компонентов | **Выделение Notification Service** | Уменьшение времени выполнения основного процесса обработки заказа; уведомления обрабатываются асинхронно |
| 4 | Аналитические сервисы обращаются напрямую к Oracle | Высокая нагрузка на транзакционную БД, снижение производительности основной системы | **Выделение Analytics Service и переход на событийную интеграцию** | Снижение нагрузки на Oracle; уменьшение количества прямых запросов аналитики к операционной БД |
| 5 | Обмен между компонентами осуществляется через общую базу данных (Shared Database) | Высокая связанность, невозможность независимого развития компонентов | **Замена обмена через БД на API и события** | Снижение количества компонентов, использующих общую БД; рост числа API и событийных интеграций | |

# 3. Что остается в монолите

На первом этапе НЕ рекомендуется изменять следующие части:

## Checkout

Причина

Критически важный бизнес-процесс.

Любая ошибка приводит к потере заказов.

---

## Order Processing

Причина

Содержит большое количество скрытых зависимостей.

Является ядром системы.

---

## Pricing

Причина

Тесно связан с Checkout.

---

## Promo

Причина

Содержит множество бизнес-правил.

---

## Payment Orchestration

Причина

Высокие финансовые риски.

---

## Delivery Routing

Причина

Используется большим количеством интеграций.

---

# 4. Целевая архитектура

## Сохраняются

- Java Monolith
- Oracle
- Checkout
- Pricing
- Promo
- Payment
- Order Processing

---

## Выделяются

- API Gateway / Integration Layer
- Order Status Service
- Notification Service
- Analytics Service

---

## Меняются интеграции

Вместо

Shared Database

используются

- REST API
- Event-driven взаимодействие

---

# 5. Архитектурные принципы

При трансформации используются:

- Strangler Fig Pattern;
- API First;
- Database per Service (по мере выделения сервисов);
- Event Driven Architecture;
- Anti-Corruption Layer для интеграции с монолитом.

---

# 6. Основные риски

| Риск | Способ снижения |
|-------|-----------------|
| Скрытые зависимости | Архитектурное обследование перед миграцией |
| Нарушение бизнес-процессов | Поэтапная миграция |
| Потеря данных | Двойная запись и контроль целостности |
| Несогласованность статусов | Выделение единого владельца жизненного цикла заказа |
| Рост сложности интеграций | API Gateway |

---

# 7. Архитектурные пробелы

Во входных материалах отсутствуют:

- допустимое время простоя;
- допустимое время миграции;
- требования к совместимости API;
- требования к консистентности данных;
- требования к производительности после миграции;
- требования к SLA новых сервисов.

До начала реализации данные параметры необходимо уточнить.
